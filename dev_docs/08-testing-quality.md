# 08. Порядок разработки, тесты и качество

## Порядок работы над любой задачей

1. **Проектирование.** Короткое описание в задаче или PR: что меняется, контракт, крайние случаи. Если меняется контракт или архитектура — запись в `09-decisions.md`.
2. **Тесты.** Пишутся до кода и падают по правильной причине.
3. **Код.** Минимум, чтобы тесты прошли.
4. **Проверка и отладка.** Все тесты пакета зелёные, линтер и типы чистые, ручная проверка сценария, если он видимый.

## Уровни тестов

| Уровень | Что | Где бежит |
| --- | --- | --- |
| unit | нормализация, манифест, глоссарий, разбор заголовков фрагментов, проверка прав, память, проверка ссылок, нормализация вопросов | `uv run pytest` без внешних сервисов |
| контракт между сервисами | общие очереди RabbitMQ объявляются knowledge и backend одинаково; сообщения публикации практики читаются в обе стороны (D-61) | `tests/contract`, в `uv run pytest` |
| integration | knowledge с Postgres (pgvector + AGE) и RabbitMQ в контейнерах; backend с Postgres; поддельный LLM и эмбеддинги | `uv run pytest -m integration` (docker) |
| e2e | весь стенд в compose, сценарии демо из `01-concept.md` через LangGraph SDK | `uv run pytest -m e2e`, перед демо и по запросу |
| leak | тесты из `07-security.md` | в integration и e2e, всегда в CI |
| deploy | правила релиза: проверки конфига и сборки web, туннель, вход в probe, генерация секретов, совместимость `deploy.py` с Python 3.9 | `uv run pytest deploy/tests` (входит в `uv run pytest`) |

CI (`.github/workflows/ci.yml`): `python` — линтер, типы и тесты без внешних сервисов; `integration` — integration и leak на образе `deploy/postgres` (pgvector + AGE) и RabbitMQ (D-41); `web`. e2e в CI не бежит; на стенде роль дымового теста выполняет проверка релиза со входом под `employee_public` (D-49).
| web | компоненты и вызовы API (Vitest), один сквозной сценарий (Playwright) | `npm test` в `web/` |

**Поддельный LLM.** Для unit и integration — детерминированная подмена OpenAI-совместимого API (фикстура), чтобы тесты не зависели от внешнего сервера и не стоили денег. Тесты с настоящей моделью помечаются `@pytest.mark.llm` и в CI по умолчанию не бегут.

## Демо-данные

Синтетический корпус по образцам заказчика (скрипт генерации в `scripts/synth/`, ручная проверка каждого документа):

| Что в корпусе | Под какой сценарий |
| --- | --- |
| Один процесс в разных областях (уже есть в образцах) | уточнение области, память |
| Документы, на которые образцы ссылаются по названию: подбор субподрядчика, контроль маржинальности, контроль поставок, инструкция по системе управления проектами | ответ по нескольким документам |
| Две редакции одного документа; один удалённый | версии |
| Регламент командировок + записи практики (суббота, такси, регион) | практика |
| 2–3 документа закрытого уровня + канарейки | права |
| Аббревиатуры из глоссария и вне его | глоссарий |
| Манифест на весь корпус | всё |

Объём 25–40 документов. Реальные образцы заказчика в git не коммитятся (папка `data/` в `.gitignore`), перед загрузкой на стенд обезличиваются.

## Набор вопросов

`eval/questions.yaml`, 37 автоматических кейсов и отдельный e2e смены редакции: простые, по нескольким документам, неоднозначные по области, по практике, на закрытые документы с разных учёток, вне корпуса, негативные. У каждого — эталон: ожидаемые пункты, краткий эталонный ответ, ожидаемый исход (`answer`, `ask_area`, `refusal`, `not_found`).

`eval/behavior-dialogues.yaml` — отдельный набор из 15 ходов для проверки ответа с источниками, коротких уточнений, пробелов в регламентах и действий в ОКК. Последовательные ходы сценария выполняются в одном диалоге. Для отдельных кейсов код проверяет необходимые и запрещённые формулировки и отсутствие источников. В отчёте сохраняется `run_id` для проверки причин расхождений в серверных событиях (D-62, D-63). [Описание прогона](../eval/README.md)

## Оценка

| Критерий | Кто проверяет |
| --- | --- |
| Каждое утверждение подтверждено фрагментом | ручная выборка |
| Совпадение со смыслом эталона | ручная выборка |
| Правильные пункты в ссылках | код |
| Уточнение области там, где нужно | код |
| Отказ / «не нашёл» там, где нужно | код |
| Утечки | только код |
| Время до первых слов и до конца ответа | код |

Текущий прогон сохраняет JSONL и отчёт `eval/reports/<дата>.md` и останавливается при утечке источника. Для проверки смысла и подтверждения утверждений предусмотрена ручная разметка 20 ответов. Автоматический судья отложен. Команды прогона и обработки разметки приведены в [описании набора](../eval/README.md).

## Замеры

- Время полной индексации корпуса; время upsert/delete одного документа.
- Попадание нужного пункта в топ-k.
- Время ответа: до первых слов и полное, отдельно для простых и составных вопросов. Цель — заметно быстрее минуты. Если Deep Agent не укладывается — урезаем число шагов, отключаем лишние встроенные возможности, отключаем рассуждения модели в guard и простых ответах.

## Приёмка первого выпуска ОКК

Проверки потока B покрывают отправку с подтверждением, дедупликацию, доступ сотрудника и администратора, переходы и историю, повтор отправки после сбоя брокера, явную ошибку Knowledge, дубликаты событий и перепроверку новой редакции. Аналитика проверяется на одном результате хода, группировке, фильтрах, изоляции прав и сроке хранения. Сквозная приёмка публикации и появления источника в чате выполняется после подключения потоков A и C.
