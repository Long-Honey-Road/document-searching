# 03. Сервис knowledge

Один процесс: HTTP API поиска (FastAPI), наблюдатель за папкой, потребитель RabbitMQ с конвейером индексации, реестр LightRAG-экземпляров. Наружу не публикуется; backend обращается к нему по внутренней сети с сервисным токеном.

## Модули

| Модуль | Ответственность |
| --- | --- |
| `config` | Настройки из `.env` (pydantic-settings), уровни доступа из YAML |
| `manifest` | Чтение и валидация `manifest.yaml`, справочник областей |
| `registry` | Таблицы `documents` и `jobs` в БД `knowledge`: что проиндексировано, какой версии, с каким хэшем, в каком workspace, статус |
| `watcher` | Наблюдение за папкой (watchdog), дебаунс, сверка с реестром, постановка задач в `index.jobs` |
| `parsing` | DOCX/PDF → markdown с сохранением нумерации пунктов (Docling; MinerU — запасной). Интерфейс `Parser` |
| `normalize` | Разбиение на пункты, заголовки фрагментов, поиск ссылок на другие документы по названию, извлечение пар «полное название (АББР)» |
| `okf` | Запись и чтение концептов OKF, коммиты в git (единственный писатель) |
| `glossary` | Глоссарий заказчика + автодополнение + разворот аббревиатур в запросе |
| `rag` | Реестр объектов LightRAG (по одному на уровень), функции LLM/эмбеддингов, вставка/удаление/запрос |
| `search` | Поиск по нескольким workspace, слияние, реранк, фильтр по области, проверка прав |
| `consumer` | Обработчики `index.jobs` и `practice.publish`, повторы, очередь ошибок |
| `api` | HTTP-эндпоинты (см. [06-contracts.md](06-contracts.md#knowledge-api)) |

Коннектор источника документов — интерфейс `DocumentSource` с одной реализацией `FolderSource`. Confluence в будущем — вторая реализация.

## Манифест

Файл `manifest.yaml` в корне папки с документами. Без записи в манифесте документ не индексируется (запрет по умолчанию).

```yaml
documents:
  - file: projects/dib-project-activity.docx
    doc_id: dib-project-activity          # стабильный id, [a-z0-9-]
    title: Проектная деятельность Дирекции ИБ
    areas: [ДИБ]                          # из справочника областей; "общий" — для всех
    access: public                        # ровно один уровень доступа из access_levels.yaml
    version: 3
    effective_from: 2026-09-01
    supersedes: dib-project-activity@2    # необязательно
```

Справочник областей — секция `areas:` в том же файле (код, название, синонимы). Ошибки валидации не роняют конвейер: документ получает статус `invalid_manifest` и виден на служебной странице.

## Уровни доступа и workspace

`config/access_levels.yaml`:

```yaml
levels:
  public:        { groups: ["*"] }               # любой вошедший пользователь
  closed_fin:    { groups: ["/levels/closed_fin"] }
```

На каждый уровень — объект LightRAG с `workspace=lvl_<level>` в БД `knowledge`. Граф AGE у каждого workspace свой (`lvl_<level>_chunk_entity_relation`). Документ принадлежит ровно одному уровню; если документ должен быть доступен двум группам — заводится уровень с обеими группами.

## Конвейер индексации

Задача `index.jobs`: `{op: upsert|delete, doc_id, version, path, sha256, job_id}`. Обработка идемпотентна по `(doc_id, version, sha256)`.

1. **parse** — файл → markdown. Нумерация пунктов («2.1.3») сохраняется.
2. **normalize**
   - Разбиение на фрагменты: пункт верхнего уровня вместе с подпунктами. Слишком длинный раздел режется по подпунктам. Для найденного документа поиск добавляет подходящие точные пункты из той же редакции OKF перед реранком (D-36). Максимум токенов — параметр.
   - Каждый фрагмент начинается служебным заголовком, который потом разбирается обратно в метаданные:
     `⟦doc=dib-project-activity v=3 clause=2.7 area=ДИБ level=public⟧ Проектная деятельность Дирекции ИБ — 2.7 Назначение РП`
   - Ссылки по названию («регламентом подбора субподрядчика») сопоставляются с названиями из манифеста через лемматизацию (`pymorphy3`). Однозначные связи пишутся в OKF. Неоднозначные названия и отсутствующие документы сохраняются отдельными списками. Связи в графе относятся к P2-B1.
   - Пары «полное название (АББР)» → кандидаты глоссария.
3. **okf** — концепт редакции пишется в `okf/docs/<doc_id>/v<version>.md` (YAML-шапка + markdown по пунктам), коммит. Старая редакция получает `status: deprecated`.
4. **index** — в workspace уровня документа: удалить предыдущую редакцию (`adelete_by_doc_id`), вставить новую с нашими фрагментами (своя функция разбиения, LightRAG не режет текст сам). id документа в LightRAG = `<doc_id>@v<version>`.
5. **registry** — статус `indexed`, время каждого шага. Ошибка шага → до 3 повторов с паузой → очередь ошибок + статус `failed` с текстом ошибки.

Одна попытка ограничена `INDEX_JOB_TIMEOUT_S` (по умолчанию 1800 с). При тайм-ауте ошибка содержит имя шага, затронутая запись документа получает `failed`, а очередь применяет обычные повторы и `regagent.dlq`. При отмене вставки LightRAG удаляется незавершённая запись этого документа в его workspace. Очистка ограничена пятью секундами, её сбой виден в логе (D-44).

Начало и завершение задач и шагов пишутся в INFO как `job=<id> doc=<id> v=<версия> step=<шаг> start|done <секунды>`. Ошибка шага отмечается `failed`. Пройденные шаги сразу появляются в `jobs.steps`. Во время подготовки и между шагами `current_step` равен `prepare`.

```sql
SELECT job_id, doc_id, version, attempts, current_step, steps, updated_at
FROM jobs
WHERE status = 'indexing'
ORDER BY updated_at;
```

`delete` — удаление из workspace, концепт в OKF помечается `status: deleted`, практика по его пунктам уходит в ОКК на перепроверку (сообщение в backend через `qc.events`).

Новая редакция → вся практика, привязанная к пунктам старой, тоже уходит на перепроверку; до решения ОКК переопределяющая запись продолжает действовать с пометкой.

## LightRAG: настройка

- Хранилища: `PGKVStorage`, `PGVectorStorage`, `PGGraphStorage`, `PGDocStatusStorage`.
- Роли моделей: EXTRACT, KEYWORD, QUERY — все через внешний OpenAI-совместимый адрес; модели задаются в `.env`.
- Язык извлечения передаётся LightRAG через `LIGHTRAG_LANGUAGE` (по умолчанию `Russian`). Глоссарий и предметные типы сущностей относятся к дальнейшему развитию.
- После извлечения — склейка синонимов по глоссарию («РП» = «руководитель проекта»).
- Поиск — только получение контекста (`aquery_data` / аналог без генерации ответа); ответ генерирует агент.
- Версию LightRAG фиксируем в `uv.lock` после проверки; любое обновление — только после зелёных тестов на утечки (см. [07-security.md](07-security.md)).

Известные риски workspace и что с ними делаем — в [07-security.md](07-security.md#изоляция-workspace-lightrag).

### Переиндексация корпуса

После обновления knowledge выполните на стенде команду в работающем контейнере. Она ставит `upsert` с `force: true` для действующих документов реестра, если они есть в валидном манифесте и в папке. Обычная очередь применяет проверку текущей редакции, файла и SHA. Повторная доставка того же сообщения подавляется по `job_id`. Новый запуск команды заново ставит задачи на текущие редакции (D-45).

```sh
docker compose --env-file .env -f deploy/compose.yaml exec knowledge \
  python -m regagent_knowledge.reindex --all
```

Так обновляются граф после изменения настроек извлечения и ссылки в OKF после изменения каталога. При запуске с хоста `--env-file` принимает конфигурацию с доступными из хоста адресами БД, брокера и папки документов.

### Проверка маркера извлечения

В текстовом режиме LightRAG ожидает строки `entity` и `relation` с полями через `<|#|>` и завершитель `<|COMPLETE|>`. На закреплённой версии LightRAG отсутствие завершителя даёт предупреждение. Тест с подставной моделью подтверждает, что полные строки при этом сохраняются, а строка связи с недостающим обязательным полем отбрасывается. Отсутствие маркера указывает на формат вывода, однако по предупреждению нельзя определить, оборвался ли ответ и сколько записей потеряно.

Сначала посчитайте такие ответы в рабочем workspace. Для выяснения причины сравните строки из нескольких записей кэша с форматом LightRAG и с признаком обрезки в логах провайдера. Текст кэша проверяйте на хосте с доступом к документам.

```sql
SELECT workspace, count(*) AS replies_without_marker
FROM lightrag_llm_cache
WHERE cache_type = 'extract'
  AND return_value NOT LIKE '%<|COMPLETE|>%'
  AND ltrim(return_value) NOT LIKE '{%'
GROUP BY workspace;
```

`LIGHTRAG_EXTRACTION_JSON=true` включает штатный JSON-формат LightRAG, если сервер модели поддерживает `response_format=json_object`. Перед включением проверьте на настоящей модели, что в ответах сохраняются ожидаемые сущности и связи. Для окончательного вывода о предупреждениях на публичном стенде нужен образец ответа из его кэша (D-46).

## Поиск

Вход: `query`, `levels` (из токена, передаёт backend), `areas` (может быть пусто), `top_k`.

1. Разворот аббревиатур кодом: без учёта регистра, кроме совпадающих с обычными словами (список строится по частоте строчных вхождений в корпусе); расшифровка добавляется к запросу, а не заменяет слово.
2. Запрос к каждому разрешённому workspace параллельно.
3. Слияние, удаление дублей, реранк.
4. Фильтр по области: фрагменты нужных областей + «общий». Если область не задана — возвращаем всё, но в ответе отмечаем, расходятся ли фрагменты разных областей (флаг `areas_diverge` и список областей) — по нему агент решает, уточнять ли область.
5. **Проверка прав**: для каждого фрагмента по заголовку берём `doc_id`, по реестру — уровень документа; уровень не входит в `levels` → фрагмент выбрасывается, пишется событие безопасности. Фрагмент без разбираемого заголовка тоже выбрасывается.
6. Порог реранкера: все ниже порога → пустой результат с флагом `low_confidence`.

Выход: список фрагментов `{fragment_id, doc_id, version, title, clause, area, kind: regulation|practice, text, score}` + флаги.

`/clause` и `/refs` проверяют права так же.

## OKF

```
okf/
  index.yaml
  glossary.yaml
  docs/<doc_id>/v<N>.md          # редакция: шапка + пункты
  practice/<practice_id>.md      # запись практики
```

Шапка редакции:

```yaml
type: regulation
title: Проектная деятельность Дирекции ИБ
doc_id: dib-project-activity
version: 3
status: active            # active | deprecated | deleted
areas: [ДИБ]
access: public
effective_from: 2026-09-01
supersedes: dib-project-activity@2
sources: [{file: projects/dib-project-activity.docx, sha256: ...}]
links: [{doc_id: subcontractor-selection, via: "регламентом подбора субподрядчика", clause: "2.4"}]
links_needing_review: [{clause: "2.5", via: "название с несколькими совпадениями", candidates: [doc-a, doc-b]}]
missing_links: [{clause: "4.4", via: "Инструкции по работе с системой управления проектами"}]
generated: {by: knowledge, at: 2026-11-27T10:00:00+07:00}
```

`clause` — пункт, в котором обнаружено название, `via` — его исходная форма. `links` содержит только однозначные сопоставления. Два остальных списка предназначены для сверки. Старые редакции могут содержать только `links`. Новые поля в публичный `/refs` не добавлены. Связи между документами живут только в OKF и отдаются через `/refs` с проверкой прав. В граф LightRAG они не добавляются (D-48).

Запись практики индексируется в workspace уровня привязанного пункта одним фрагментом с заголовком `⟦practice=<practice_id> doc=<doc_id> clause=<clause> mode=clarifies|overrides area=<area> level=<level>⟧`.

Шапка практики: `type: practice`, `practice_id`, `binds: [{doc_id, clause}]`, `mode: clarifies|overrides`, `areas`, `verified: {by, at}`, `status`, `source_ticket`. Уровень доступа практики не хранится в шапке как источник истины — код берёт его от привязанного пункта.

## Глоссарий

- `okf/glossary.yaml` — записи `{abbr, full, source: customer|auto, docs: [...]}`.
- Автодополнение: одинаковая расшифровка в ≥2 документах и без конфликта → принимаем; одно вхождение → кандидат; конфликт → список «на сверку».
- TPS и TSS не склеиваем до ответа заказчика.
