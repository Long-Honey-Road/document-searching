# 07. Безопасность и права доступа

Принцип: права определяет и проверяет только код. Модель их не видит, не выставляет и не передаёт. Защита в несколько слоёв — ошибка одного не должна приводить к утечке.

## Слои

1. **Запрет по умолчанию.** Документ без записи в манифесте или с неизвестным уровнем не индексируется.
2. **Физическое разделение.** Отдельный workspace LightRAG (свои таблицы-разделы и свой граф AGE) на каждый уровень. Поиск идёт только по workspace уровней пользователя.
3. **Личность только из токена.** Подпись JWT, issuer, audience, срок — проверяются в backend. Уровни вычисляются из групп токена кодом.
4. **Повторная проверка каждого фрагмента** в knowledge по реестру (`doc_id` → уровень). Фрагмент без разбираемого заголовка выбрасывается. Каждое срабатывание — событие безопасности в логе.
5. **Практика** получает уровень пункта, к которому привязана; привязка к пунктам разных уровней запрещена при публикации. Backend проверяет роль `admin` и берёт разрешённые уровни из учётной записи. Knowledge проверяет все привязки по текущему реестру при публикации и поиске.
6. **Кэши** ключуются набором уровней пользователя; общих кэшей между уровнями нет. Кэш ответов LLM у LightRAG — внутри workspace.
7. **Память о пользователе** ключуется `sub` из токена; права в ней не хранятся.
8. **Сеть.** Наружу только Caddy. knowledge, Postgres, RabbitMQ, TEI — во внутренней сети. knowledge требует сервисный токен.
9. **Журнал** кто спросил и какие документы вернулись.

## Изоляция workspace LightRAG

Что известно о качестве этой функции:

- В истории LightRAG был баг: хранилища Postgres брали workspace общего подключения вместо workspace экземпляра, и все экземпляры писали в первый инициализированный. Исправлен.
- В режиме сервера LightRAG заголовок выбора workspace игнорировался в `/query`, и контекст собирался из workspace по умолчанию — утечка между workspace. Рабочий обход у пострадавших — свой сервис с отдельным объектом LightRAG на каждый workspace. Мы так и делаем: сервер LightRAG не используем.
- В соседнем проекте (RAG-Anything) вызовы без явного workspace падали на workspace по умолчанию процесса — первый инициализированный. Класс ошибки: любой код, вызывающий общие функции LightRAG без явного workspace.
- Векторный индекс HNSW в Postgres общий для всех workspace: поиск идёт по всему индексу, затем фильтруется по workspace. На больших объёмах это медленно; при нашем объёме (сотни документов) — не проблема, но следим за полнотой выдачи.

Что делаем:

- **Workspace по умолчанию процесса — пустой служебный.** Первым инициализируется объект `lvl__sentinel` без данных: если какой-то путь упадёт на workspace по умолчанию, он попадёт в пустоту, а не в чужой уровень.
- **Канарейки.** В каждый закрытый уровень индексируется служебный документ с уникальной строкой-маркером. Тесты и проверка при старте knowledge ищут маркеры из всех остальных уровней: найден чужой маркер — сервис не поднимается (fail closed), тест красный.
- **Слой 4 обязателен** даже при исправной изоляции.
- Версия LightRAG закреплена в `uv.lock`; обновление — только с зелёными тестами на утечки.
- Запасной план при найденной утечке, которую не закрыть быстро: отдельная БД Postgres на уровень (физическая изоляция подключений).

## Тесты на утечки (обязательны в CI)

- Пользователь каждого уровня задаёт вопросы про закрытые документы других уровней: ни одного чужого фрагмента в ответе `/search`, `/clause`, `/refs` и в итоговом ответе агента.
- Канарейки всех уровней (см. выше).
- Подмена: модель «просит» инструмент искать с чужим уровнем — у инструментов нет такого аргумента; тест проверяет схему инструментов.
- Память: пользователь A не видит памяти пользователя B; `remember` не принимает тип вне белого списка.
- Практика с привязками к пунктам разных уровней не публикуется.
- Без токена / с просроченным / с чужим issuer — 401 на всех маршрутах backend; knowledge без сервисного токена — 401.

## Угрозы и ответы

| Угроза | Ответ |
| --- | --- |
| Подбор паролей | защита от перебора в Keycloak, лимит по IP |
| Расход GPU посторонними | только именные учётки, лимит на учётку, лимит длины вопроса |
| Промпт-инъекция в вопросе | guard-узел, права не зависят от модели, инструменты без аргументов прав |
| Промпт-инъекция в тексте документа | документы — данные; системный промпт требует не исполнять инструкции из фрагментов; на демо корпус наш |
| Индексация поисковиками | `X-Robots-Tag: noindex`, robots.txt |
| Утечка через ошибки | одинаковый 404 для «нет прав» и «нет документа» |
| Секреты в репозитории | `.env` в `.gitignore`, `.env.example` без секретов |
